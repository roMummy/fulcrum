# Multi Bot Admin UI/UX 调性与配色设计

## 背景

`Multi Bot Admin` 是一个多渠道机器人后台，核心工作不是展示营销信息，而是让管理员持续处理机器人、渠道、会话、消息、插件、任务队列、日志和告警。

本次 UI/UX 重构前，已确认采用「运维控制台浅色系」作为主方向。该方向保留现有浅色后台的易读性，同时降低大面积渐变、过大圆角和装饰感，改为更稳定、更高密度、更适合扫表和处理异常的控制台体验。

## 设计目标

1. 让用户进入系统后能先判断运行态势，再进入具体对象处理问题。
2. 让渠道状态、插件运行状态、任务队列和日志告警比普通配置项更醒目。
3. 让长表格、详情页、表单和弹窗在高信息密度下仍然清晰。
4. 让视觉风格偏专业运维控制台，而不是营销页、展示页或过度柔和的 SaaS 门户。
5. 首阶段优先建立统一视觉语言，不引入复杂主题切换；深色监控屏可作为后续独立增强。

## 调性关键词

- 冷静：大面积背景使用低饱和浅灰蓝，避免高对比背景干扰排障。
- 清晰：组件边界明确，状态色职责固定，主要动作和危险动作不能混淆。
- 高密度：减少大 hero、宽松卡片和重复说明，优先服务列表、指标和操作流。
- 可靠：色彩不追求潮流感，强调稳定、可维护、可长期使用。
- 运维感：通过状态条、紧凑指标、清晰表格和分组导航体现系统运行管理属性。

## 色彩系统

### 基础色

| Token | 色值 | 用途 |
| --- | --- | --- |
| `--bg` | `#F5F7FB` | 页面主背景 |
| `--surface` | `#FFFFFF` | 卡片、表格、弹窗主体 |
| `--surface-soft` | `#F8FAFD` | 次级块、表头、浅底标签 |
| `--surface-muted` | `#EEF2F7` | 导航 hover、禁用态、弱提示背景 |
| `--border` | `#D8E0EC` | 常规边框 |
| `--border-strong` | `#B8C3D4` | 表格分隔、聚焦边框、重要区域边界 |
| `--text` | `#172033` | 主文本 |
| `--text-soft` | `#3B465C` | 次级标题、表格正文 |
| `--muted` | `#6A7383` | 辅助说明、时间、弱信息 |

### 品牌与操作色

| Token | 色值 | 用途 |
| --- | --- | --- |
| `--primary` | `#195BDB` | 主按钮、当前导航、关键链接、聚焦态 |
| `--primary-strong` | `#1246A8` | 主按钮 hover、重要操作强调 |
| `--primary-soft` | `#E8EFFD` | 主色浅底标签、选中背景 |
| `--primary-border` | `#AFC4F6` | 选中边框、轻量强调边框 |

蓝色只用于“指令、选中、当前焦点和关键入口”。不要把普通信息块全部染蓝，避免页面重新变成单一蓝色调。

### 状态色

| 状态 | Token | 色值 | 使用规则 |
| --- | --- | --- | --- |
| 正常 / 运行中 | `--success` | `#15806D` | RUNNING、SUCCESS、在线、已启用 |
| 正常浅底 | `--success-soft` | `#E7F6F1` | 成功 badge、健康提示背景 |
| 风险 / 等待处理 | `--warning` | `#D98A14` | WARNING、待处理任务、配置缺失但未阻断 |
| 风险浅底 | `--warning-soft` | `#FFF4DF` | 风险提示、待处理状态底色 |
| 异常 / 阻断 | `--danger` | `#C83F54` | ERROR、失败任务、异常渠道、危险按钮 |
| 异常浅底 | `--danger-soft` | `#FDECEF` | 错误提示、危险确认区域 |
| 信息 / 中性 | `--info` | `#436382` | INFO、普通系统事件 |
| 信息浅底 | `--info-soft` | `#EAF1F8` | 普通说明提示 |

状态色必须语义固定：绿色不能用于普通装饰，红色不能用于非危险强调，琥珀色专门承载“需要看但不一定失败”的状态。

## 组件风格

### 布局

- 应用主结构保留顶部菜单栏，顶部导航仍作为主要模块入口。
- 顶部栏分为三段：左侧品牌与系统名，中间主模块菜单，右侧当前用户、环境筛选、全局入口和账号操作。
- 顶部菜单需要降低胶囊感，改为更克制的标签式导航；当前模块用底部强调线、浅底和主色文字共同表达。
- 当一级菜单过多时，优先将低频入口收进“更多”或模块内二级导航，不改为左侧主导航。
- 页面主体宽度不再依赖大 hero 视觉，优先显示当前模块的筛选、摘要指标、列表和操作。
- 首页仪表盘可以保留较强的总览感，但不使用营销式大标题区。

### 圆角与阴影

- 常规卡片圆角使用 `8px`。
- 按钮、输入框、badge、chip 使用 `6px` 到 `8px`。
- 弹窗可以使用 `10px`，但避免过大的柔和圆角。
- 阴影只用于弹窗、浮层和少数悬浮区域；普通卡片以边框和背景区分。

### 卡片

- 卡片只用于指标组、表单容器、详情分区、重复列表项和弹窗。
- 页面分区不做多层卡片嵌套；如果需要分组，使用标题、边框、表格行和浅底块。
- 指标卡应使用左侧状态色条或顶部细线表达类别，不使用大面积渐变。

### 表格

- 表格是本系统的核心组件，需要优先重构。
- 表头使用 `--surface-soft`，行分隔使用 `--border`。
- ID、状态、时间、操作列保持稳定宽度。
- 操作列使用紧凑按钮或图标按钮，避免每行操作造成高度膨胀。
- 异常行可使用浅色背景或左侧状态条，但不能整行高饱和。

### 按钮

- 主按钮只用于创建、保存、执行关键动作。
- 次按钮用于返回、刷新、重载、查看等普通动作。
- 危险按钮只用于删除、停用、退出、危险恢复类操作。
- 小按钮用于表格操作，尺寸保持稳定，避免文本撑开布局。

### Badge 与 Chip

- Badge 表示状态，必须使用固定状态色。
- Chip 表示筛选、计数、标签和弱操作。
- 状态 badge 文案尽量保留 `RUNNING`、`ERROR`、`SUCCESS` 等英文运行态，同时在必要处配中文解释。

## 页面优先级

第一阶段重构应优先处理这些高收益页面：

1. `base.html` 与全局导航：建立统一框架、间距、按钮、状态组件。
2. `dashboard.html`：把总览从卡片堆叠改为运维态势入口。
3. `channels.html` 与 `channel_detail.html`：渠道状态、Provider、Webhook、群列表和关键操作需要更清楚。
4. `plugins.html`、`plugin_detail.html`、`plugin_runtime.html`：插件绑定、运行态、迁移状态和调度结果需要统一状态表达。
5. `conversations.html`、`messages.html`、`conversation_detail.html`：消息流转和会话筛选需要更紧凑。
6. `monitoring.html` 与 `errors.html`：告警、日志和审计要成为排障中心。

## 明确不做

- 第一阶段不做深色主题切换。
- 第一阶段不做全新品牌插画、装饰背景或营销首页。
- 第一阶段不引入新的前端框架。
- 第一阶段不重构后端业务流程，除非 UI 必须依赖小范围数据结构整理。
- 不使用大面积紫色、蓝紫渐变、暖米色或单一蓝色铺满页面。

## 后续验收标准

1. 页面第一屏能看出当前模块的核心状态和下一步操作。
2. 主要列表在 1366px 宽度下仍能稳定阅读，不出现按钮和文本明显挤压。
3. 状态色在所有页面语义一致。
4. 普通配置、运行状态、告警风险三类信息有清晰视觉层级。
5. 移动端可以完成查看和基础操作，但后台高密度工作流优先保证桌面体验。
6. 重构后的 CSS token 能覆盖大多数页面，不再依赖大量零散硬编码颜色。
