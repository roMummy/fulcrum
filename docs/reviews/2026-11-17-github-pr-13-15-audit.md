## 已复现的合并阻断项

### 1. [P1] PR #15 会把已有 QQMusicApi 绑定切换到网易云

位置：`plugins/music/config.toml:26`、`:43`；`plugins/music/plugin.py:274`；`app/services/plugin_directory.py:1828`（均为 PR #15 提交内行号）。

新增清单默认值 `provider = "netease"`，运行时先合并插件默认值，再合并机器人和群配置。已有绑定虽然配置了 QQMusicApi 的 `api_base`，但没有新增的 `provider` 字段，最终会带着 `provider="netease"` 进入插件。

最小复现使用真实的 `_build_directory_context`，不访问外部接口：

- 已保存配置：有 QQMusicApi 服务地址，没有 `provider`。
- 直接调用 `_load_config`：返回 `qqmusic`。
- 按真实消息调用路径合并默认值后再调用：返回 `netease`。

PR 自带“旧配置保留 QQMusicApi”的测试只直接调用 `_load_config`，没有覆盖消息链路的默认值叠加，因此没有发现该问题。

影响：升级后用户已有音源、账号及会员策略可能失效，实际请求改发网易云和第三方 meting。推荐维持当前绑定音源；新增网易云应由用户明确选择。若引入音源字段，应一次性写入明确配置，保持单一业务路径，不增加长期隐式推断分支。

### 2. [P1] PR #15 撤回匹配可能把另一条同文消息标为已撤回

位置：`app/services/message_actions.py:329`、`:336`、`:355`。

入站消息的微信本地、服务器编号保存在 `raw_request_json.native_ids`，而撤回匹配仅比较 `Message.external_message_id`。后者可能是事件 ID，无法命中微信服务器编号。代码随后按“正文、发送者、最近十分钟”选择最新一条消息。

最小复现：同一成员先后发送两条“好的”，它们有不同的事件 ID 和微信服务器编号；收到撤回第一条的通知，通知含第一条的真实服务器编号。代码实际把第二条标为 `revoked`，第一条仍为 `received`。

推荐先匹配明确的微信编号；无法唯一确认原消息时保留撤回通知，不按相同正文猜测并修改其他消息。该问题无需改变微信实际撤回行为即可导致后台历史状态错误。

### 3. [P2] PR #15 的全局测试隔离覆盖了独立进程的数据库配置

位置：`tests/conftest.py:11`、`:16`、`:17`。

现有 `scripts/run_tests_isolated.sh` 为每个测试文件分配独立的 `DATA_DIR`、`DATABASE_URL` 和日志目录，并以四个进程并行运行。新增 conftest 无条件把它们全部改成仓库下固定的 `.run/test-runtime/pytest/test.db`。

最小复现：两个逻辑测试进程分别传入不同 SQLite URL，加载 conftest 后得到完全相同的数据库 URL。并行运行或同时启动两轮测试时失去隔离，存在清表、锁竞争和结果互相污染的风险。这是单独复现的工程问题，不能把现有 CI 的失败直接归因于它。

推荐保留测试防误连能力，同时尊重受控的独立测试目录，未指定目录时为本次运行创建唯一目录；不连接或清理真实业务数据库。
