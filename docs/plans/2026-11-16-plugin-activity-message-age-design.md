# 插件活动排序与入站消息时效设计

## 用户明确的结果

保留已确认正常的图表底部时间点读数。企业插件目录和平台插件管理都把最近有活动的插件排在前面。按渠道原始发送时间判断消息时效：接收时超过十分钟的消息正常入库，不创建插件指令任务。

## 插件排序

沿用现有批量统计接口，在日志聚合中同时返回每个插件的最近真实活动时间。真实命中或实际调用算活动，未命中扫描不算；平台汇总全部企业，企业严格使用当前企业范围。排序使用历史最近活动，不受 24h／7d／30d 图表筛选影响；时间相同和没有活动时保留原来的相对顺序。

共用前端脚本移动既有卡片节点，保留开关、设置、搜索和筛选。相比只按当前范围的调用次数排序，这能准确反映“最近”；相比每张卡片单独请求，不增加数据库往返次数。

## 消息时效

把现有原始时间解析收敛到公共入站时间策略模块，支持渠道已使用的秒、毫秒、ISO 与 datetime。缺少有效原始时间时保持即时事件处理，不能把缺失或零值当成 1970 年而误丢实时消息。补齐现行适配器已有发送时间到标准 details.timestamp 的映射。

入站完成原始事件、消息及正常资料落库后，在创建 plugin_dispatch 任务前判断时效。超过 600 秒返回 storage_only、skipped、stale_message，保存原时间、年龄和原因，不调用插件、群功能或 AI。恰好 600 秒仍允许处理。保留采集关闭、自发消息、显式跳过和免打扰规则的现有职责。

消费插件队列时再次使用同一规则，覆盖入队后积压及已有任务；AI 准备和最终结果下发同样检查，防止慢模型或积压的 AI 任务迟到执行。手动执行和定时任务不属于入站消息，不套用此规则。不清理已有业务数据或批量删除任务。

## 验证范围

验证真实活动与扫描区分、跨企业隔离、切换图表范围时排序稳定和两类页面的实际浏览器顺序。验证十分钟边界、各种实际时间格式、缺失时间、旧消息入库不入指令队列、正常消息仍可入队，以及插件／AI 队列消费与下发前的拦截。只执行直接相关轻量测试、Python AST、JavaScript 语法和 diff 检查；按要求中文提交，未运行全量时如实记录。
