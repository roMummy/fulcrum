# 微信 iPad 二维码运行状态精简设计

## 问题

874 取码接口同时返回二维码短链接和 Base64 图片。当前实现把完整回包与 Base64 图片重复写入 `channels.runtime_info_json`，真实回包约 134 KB，超过 MariaDB `TEXT` 字段 64 KB 上限，导致租户页面点击“获取二维码”时返回 500。

## 方案选择

采用短链接运行态方案：SaaS 只持久化二维码 UUID、二维码短链接、过期时间、刷新次数和经过精简的调用摘要。Base64 图片与包含 Base64 的原始取码回包不进入渠道运行状态。

不采用以下方案：

- 不把字段扩大为 `MEDIUMTEXT`，避免渠道表长期保存重复图片数据。
- 不增加文件存储或缓存层，当前 874 已提供可直接展示的二维码 URL，没有新增基础设施的必要。

## 数据流

1. 租户在账号接入向导创建微信 iPad 草稿。
2. SaaS 使用平台统一维护的协议服务地址调用 874 `LoginGetQR`。
3. 服务层提取 UUID、二维码 URL 和过期时间，同时把原始回包压缩为消息、返回码、HTTP 状态和字段清单。
4. 渠道运行状态只保存上述短字段。
5. 页面继续使用 `/channels/{id}/wechat-ipad/qrcode-image`，该路由重定向到二维码 URL，浏览器直接显示图片。

## 错误处理

- 874 未返回二维码 URL 时，本次取码明确标记为失败，不再回退保存 Base64。
- 每次写入运行状态前删除历史 Base64 字段，旧数据不会继续沿登录链路传播。
- 失败回包也只保存结构化摘要，避免异常载荷再次撑大运行状态字段。

## 验证范围

- 定向测试覆盖超大 Base64 回包不会进入 `runtime_info_json`。
- 定向测试覆盖二维码 URL 仍可通过页面图片路由展示。
- 部署后使用真实 874 服务重新走租户接入草稿与取码接口。
