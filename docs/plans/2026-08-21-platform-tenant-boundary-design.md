# 平台与企业双后台边界设计

## 背景

当前系统已经分开平台会话和租户会话，但产品语义仍混用了三类入口：平台管理员、企业所有者、需要手工输入租户编码的企业员工。从旧后台继承的监控、全局日志、服务重启、实验台和开放接口页面又挂在租户路由下，造成“身份已隔离，产品边界未隔离”。

## 目标

对外只保留两个清晰后台：

- 曜枢 AI 平台管理后台：供 SaaS 平台方员工使用，不属于任何租户，不输入租户编码。
- 企业租户后台：供企业所有者和企业员工使用，只能访问当前企业数据和业务功能。

本次不改动已确认的 `multi-bot-saas` 内部命名、“曜枢 AI”对外品牌、套餐订单、机器人额度和试用防滥用规则。

## 身份与登录

### 平台员工

- 身份来源固定为 `PlatformUser`。
- 入口固定为 `/platform/login`。
- 登录表单只接收平台用户名和密码，不接收租户编码。
- 平台会话只能访问 `/platform/**`，不能因为同名账号获得企业会话。
- 首版仍保留 `platform_admin` 单一全权角色，暂不扩展平台运营、审核员等更细角色。

### 企业用户

- 身份来源固定为 `TenantUser`。
- 产品入口统一为 `/login`，使用全局唯一手机号和密码登录。
- 企业所有者与企业员工共用同一个后台，通过 `is_owner` 和 `role` 决定租户内权限。
- 新增企业员工时必须录入手机号，保持全局唯一，从而由账号自动确定 `tenant_id`。
- 删除 `/employee/login` 及“租户编码 + 用户名”认证链，旧路径直接返回 `404`。
- 存量未填手机号的企业员工不自动伪造手机号，由企业管理员补充后才能使用新登录入口。

## 路由与权限边界

### 平台后台

下列功能必须使用平台会话，并移入 `/platform/**`：

- 服务运行监控和告警处理；
- 应用全局原始日志；
- 服务重启；
- 租户、套餐、订单、额度和机器人绑定审核。

服务重启和告警状态变更必须校验平台 CSRF，不再复用旧 `admin/ops/readonly` 角色判断。

### 企业后台

企业顶部导航只保留：

- 总览；
- 机器人；
- 渠道与执行器接入；
- 插件；
- 会话和消息；
- 套餐、订单和机器人额度；
- 企业员工与订阅信息。

企业会话访问旧 `/monitoring`、`/errors`、`/lab` 和 `/open-api/apps` 页面时统一返回 `404`，避免通过收藏链接或手工输入路径绕过导航边界。机器签名认证的 `/api/open/**` 不在本次移除范围，避免破坏已存在的对接。

## 数据流

1. 平台员工登录后生成仅在 `/platform` 路径回传的平台 Cookie。
2. 企业用户使用手机号登录，服务端从 `TenantUser` 记录恢复可信 `tenant_id`。
3. 企业请求继续由 `tenant_scope` 强制租户过滤。
4. 平台运维页面使用平台数据库会话，不进入任何单租户上下文。

## 错误处理与旧逻辑清理

- 平台 Cookie 和企业 Cookie 继续保持独立，不做自动身份升级。
- 企业手机号重复时拒绝创建或修改员工，不暴露已占用账号的企业。
- 删除旧企业员工 Router、租户编码认证函数和对应模板，不保留跳转、别名或隐式降级。
- 旧租户运维页面使用 `404` 而不是 `403`，避免向企业用户暴露平台内部能力。

## 轻量验证

当前研发阶段只执行与本次边界调整直接相关的验证：

- 平台登录和企业手机号登录定向测试；
- 企业员工手机号唯一性与权限测试；
- 租户访问平台运维路由的阻断测试；
- 平台监控、日志和重启路由的身份与 CSRF 测试；
- Python 语法检查和模板关键文案检查。

不在本次运行全量回归或完整 Playwright。
