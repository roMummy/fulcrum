# 曜枢 AI 通用渠道与租户隔离运行设计

## 1. 背景

`multi-bot-saas` 从 `multi-bot-admin` 复制建立时，微信 iPad、Windows 微信、企业微信和 Telegram 的适配器、消息处理与渠道专项服务均被保留。后续 SaaS 首期为了优先交付企业微信，并规避旧后台轮询器使用全局数据库会话产生的跨租户风险，主动隐藏了非企微入口、拒绝非企微渠道写入，并停止从 Worker 主循环调用 Telegram 与微信协议轮询器。

当前产品已经定位为全渠道智能机器人运营平台，商业模型也只依赖通用机器人额度，但渠道后台和运行时仍以企业微信为主线。此次研发需要恢复已有多渠道能力，同时把租户隔离和执行抽象补完整，不能简单恢复旧的全局扫描逻辑。

## 2. 目标

1. 租户可创建和管理企业微信、微信 iPad 协议、Windows 微信和 Telegram 渠道。
2. 页面、服务端校验、仪表盘和后台调度统一读取同一份渠道定义，不再分别硬编码渠道类型。
3. 消息收发、入站标准化、健康检查和后台轮询依赖通用渠道能力接口，不依赖 Provider 节点模型。
4. Telegram 轮询以及微信 iPad 心跳、消息同步和登录恢复必须在可信租户上下文中执行。
5. 企业微信 Provider 节点继续作为 `workwechat` 的一种远端执行方式，但不成为其他渠道或商业模型的依赖。
6. 删除本次范围内的企微唯一限制和对应测试，不保留旧允许列表、兼容别名或双轨校验。

## 3. 非目标

- 本轮不新增尚无真实适配器的渠道。
- 本轮不把 OpenClaw 或模拟器开放为租户可购买的正式渠道。
- 本轮不重写现有微信 iPad、Windows 微信或 Telegram 协议实现。
- 本轮不统一所有渠道专项详情页；专项能力仍由能力声明决定是否展示。
- 本轮不修改 `multi-bot-admin`，只把它作为已有能力的只读参考。

## 4. 统一渠道目录

新增集中式 `ChannelTypeDefinition`，每个正式渠道必须声明以下信息：

- `code`：数据库保存的稳定渠道类型。
- `label`：面向租户展示的渠道名称。
- `summary`：创建入口中的简短说明。
- `adapter_factory`：构造 `BaseChannelAdapter` 的工厂。
- `capabilities`：发送、入站、健康检查、群聊、联系人、登录、后台轮询等能力集合。
- `runtime_mode`：`remote_executor`、`platform_polling` 或 `webhook`。
- `config_fields`：创建和编辑需要的字段、必填条件及敏感属性。
- `requires_executor_binding`：是否必须绑定远端执行端账号。

首期正式目录：

| 渠道 | 类型 | 运行方式 | 核心能力 |
| --- | --- | --- | --- |
| 企业微信 | `workwechat` | 远端执行端主动领取任务 | 收发消息、群聊、联系人、健康状态 |
| 微信 iPad 协议 | `wechat_ipad` | 平台按租户轮询协议服务 | 收发消息、登录、心跳、联系人、群聊 |
| Windows 微信 | `wechat_winauto` | HTTP 执行端与 Webhook | 收发消息、群聊、健康状态 |
| Telegram | `telegram` | Webhook 或平台按租户轮询 | 收发消息、健康状态 |

适配器注册表必须根据渠道目录解析适配器。未知渠道类型直接拒绝，不再静默降级到通用 HTTP 适配器。

## 5. 配置与页面

渠道列表页从渠道目录生成类型选择器和配置元数据。前端只负责根据已选择类型显示相关字段，服务端必须再次按定义验证，不能信任隐藏字段或浏览器状态。

- 企业微信显示执行端节点和账号绑定字段。
- 微信 iPad 显示 API Base、账号标识、设备标识和可选代理字段。
- Windows 微信显示 API Base、访问凭证和执行端配置字段。
- Telegram 显示 Bot Token、可选 API Base、Webhook 路径和私聊策略字段。

编辑时渠道类型保持不可变，避免同一渠道记录在不同协议之间转换后残留密钥、运行状态和外部账号绑定。需要切换类型时创建新渠道并停用旧渠道。

页面只展示渠道声明支持的专项操作。通用页面不得出现“所有渠道都需要 Provider 节点”等错误提示。

## 6. 通用运行能力

`BaseChannelAdapter` 继续负责单个渠道的协议行为，并补充明确的能力声明。通用出站服务只依赖适配器返回的标准结果：

- `adapter_type`
- `ok`
- `status`
- `external_status`
- `external_message_id`
- `error_code`
- `error_message`
- `raw_request`
- `raw_response`

业务服务不读取具体 Provider 类型。企业微信适配器内部可以调用远端执行端任务链路，其他适配器可以直接请求 API，但对上层返回相同结果结构。

入站仍统一进入 `ingest_inbound_event`，由渠道目录解析适配器并完成标准化。Webhook、轮询和远端执行端上报最终都进入同一租户范围内的消息、插件和审计链路。

## 7. 租户隔离调度

新增通用渠道运行协调器，执行顺序固定为：

1. 使用平台会话只读取有效租户主键。
2. 对每个租户建立 `tenant_scope(tenant_id)` 和租户数据库会话。
3. 在租户会话内查询已启用且具有后台任务能力的渠道。
4. 根据渠道目录调用对应的轻量运行任务。
5. 运行结果、错误、心跳和游标只写回当前租户数据。

Telegram 使用已有 `poll_telegram_channel`，但数据库会话由协调器传入。微信 iPad 的消息同步、心跳和自动恢复同样使用当前租户会话。禁止运行器自行打开全局 `SessionLocal()` 并扫描全部渠道。

每个渠道任务保留独立执行间隔和游标，单个渠道失败只记录该渠道错误，不中断其他租户或其他渠道。企业微信远端执行端继续通过现有授权、心跳和任务领取接口运行，不进入平台主动轮询。

## 8. 仪表盘与产品描述

企业后台首页改为通用渠道视角：

- “在线企业微信账号”改为“在线渠道”。
- 机器人列表中的“企业微信账号”改为“渠道”。
- 无在线企微的风险提示改为无在线渠道或具体异常渠道提示。
- 渠道统计按统一状态字段汇总，不把某个协议作为产品健康度的唯一依据。

公开营销首页继续使用全渠道描述，可明确列出“微信、企业微信、Telegram 等渠道”，但不承诺尚未接入的协议。

## 9. 错误处理

- 未注册渠道类型：拒绝创建或运行，返回 `channel_type_not_supported`。
- 缺少必填配置：允许以停用状态保存；启用和执行时返回具体缺失字段。
- 不支持的能力：页面不展示入口，服务端调用返回 `channel_capability_not_supported`。
- 远端执行端未绑定：只影响要求远端执行端的渠道。
- 单渠道轮询失败：更新该渠道状态并记录错误，不中断整个 Worker。
- 租户已到期或不可执行：协调器跳过其主动任务，不绕过现有订阅策略。

## 10. 测试策略

本阶段只执行与本次改动直接相关的轻量测试：

1. 渠道目录注册、未知类型拒绝和配置校验测试。
2. 四种正式渠道的创建、列表和详情入口测试。
3. 企业微信绑定字段与其他渠道字段隔离测试。
4. 仪表盘通用渠道文案和统计测试。
5. Telegram 与微信 iPad 调度的租户隔离测试。
6. 适配器注册和标准结果契约测试。
7. Python 语法检查与 `git diff --check`。

不运行完整历史回归、完整端到端测试或真实第三方渠道请求；真实账号联调在部署后使用测试账号单独验证。
