# 群资料公告与成员顺序设计

日期：2026-11-14。用户已确认按推荐方案直接实现，保留群内置顶消息的能力提示。

## 页面与业务结果

- 沿用群详情的「资料」标签，在基本信息下显示群公告正文或摘要、来源、获取时间与读取状态，继续使用当前后台的紧凑排版。
- 微桥的页头按钮改为「同步群资料」，复用已有单群同步 POST，同时读取成员与群公告；任务完成后留在用户所在标签。
- 群内置顶消息保留独立说明区域，当前显示「当前渠道暂不支持读取」，不把未接入能力展示成空列表。
- 成员统一按在群群主、在群管理员、在群普通成员排列，同角色按最近发言降序，无发言记录排在同角色末尾；已退群成员统一放在全部在群成员之后。
- 群主身份优先使用已同步的 `owner_external_id`，避免成员快照未写 role 时群主仍被归为普通成员。

## 已核实的数据边界

- 公告首先接入微桥现有 `get_group_notice` 命令。2026-11-14 读取的官方长轮询文档：`https://wechat.vbzm.cn/documents/8080/long-poll`，只读命令参数为 `room_id`。
- 成功结果包含 `room_id`、`cached_notice_found`、`summary`、`html`、`html_cached`。该接口读取手机本机缓存，不触发下载，未发现缓存不能证明群里没有公告。
- 当前长轮询文档没有找到群内置顶消息读取接口，不能借用朋友圈置顶字段，也不新增未经协议证实的命令。
- 其他渠道本次保留现有资料同步方式；尚未接入公告结果的渠道明确显示「当前渠道暂未接入公告读取」，不宣称底层协议永远不支持。

## 架构与存储

- 新增 `app/services/chatroom_profile.py`，集中处理公告文本快照、公告资料视图及群成员排序，供现有详情构建函数复用。
- 公告快照只保存到本群 `Chatroom.extra_json.group_notice`，保留群功能、媒体和目录资料等已有键，无数据库迁移、无依赖变更。
- 公告 HTML 转为安全纯文本后展示，保留段落与列表换行；不直接渲染设备返回的原始 HTML，不自动请求其中的外部资源。
- 快照记录成功获取时间、请求创建时间和最近读取错误。失败保留此前已获取的正文，提示本次读取失败；未缓存和仅摘要分别说明，不冒充「无公告」或「最新公告」。
- 结果依照任务保存的群 ID 定位，并检查租户、渠道及回报群 ID。旧请求晚到不能覆盖新请求的结果；重复回报继续复用已有任务幂等边界。
- 成员排序直接处理 ORM 成员及原始时间，避免按中文角色文案或已格式化时间猜测身份与先后。企微、微桥、咕嘎共用的详情构建与 iPad 详情使用同一个排序函数，删除微桥覆盖角色顺序的旧排序。

## 权限与异常

- 复用现有受租户隔离的群详情和同步路由、运营权限、CSRF、任务进度与审计，不新增第二套入口。
- 手机返回缺失字段、错误群 ID 或读取失败时，任务终态明确失败并返回正常命令回报响应，避免让手机因 HTTP 500 反复卡在同一结果。
- 「资料」标签只展示已保存快照，GET 不主动创建查询任务；用户通过明确的同步操作更新。

## 验证范围

- 定向验证角色优先级、同角色活跃顺序、无记录顺序、退群置底与群主 ID 识别。
- 验证公告正常正文、仅摘要、未缓存、失败保留、非法 HTML、错误群、跨租户、晚到及重复结果。
- 页面验证资料展示、置顶提示、同步时两个命令与标签保留、CSRF 与只读权限，并检查常用桌面/手机宽度。
- 仅执行与本次直接相关的轻量测试；真实手机缓存、群公告与群内置顶的真机行为另行如实标记，不声称已完成全量回归。
