# Multi Bot SaaS 多租户改造设计

## 1. 背景

当前 `multi-bot-admin` 是一个 FastAPI、SQLAlchemy 和 Jinja2 组成的单体应用，已经具备机器人、渠道、会话、消息、插件、任务队列、企业微信 Provider、开放接口和运行监控等能力。

本次不直接改造现有生产项目，而是复制出独立项目 `multi-bot-saas`。现有项目及线上数据继续保持不变，新项目采用独立 Git 仓库、独立数据库和独立部署配置。SaaS 功能稳定后，再通过专用迁移脚本将现有数据导入新系统中的“自营租户”。

## 2. 已确认的产品边界

- SaaS 采用共享应用、共享 MariaDB、业务数据按 `tenant_id` 隔离的模式。
- 平台由运营方统一部署，客户只在自己的 Windows PC 上部署企业微信 Provider。
- 一个租户支持多个员工账号、多个 Provider 节点和多个企业微信账号。
- 一台客户电脑定义为一个 Provider 节点，一个节点可以承载多个企业微信账号。
- 首期由平台管理员创建租户，不开放用户自主注册，不接入在线支付。
- 套餐首期只限制 Provider 节点数，不限制员工数、企微渠道数或消息量。
- 首期只对外提供企业微信 PC Provider 能力。
- 其他渠道在租户界面中隐藏并禁止创建，底层旧适配器代码暂时保留。
- 首期保留现有 FastAPI + Jinja2 页面体系，不同步重写 Vue 前端。
- 平台管理员使用独立入口；租户员工采用租户管理员、运营人员、只读人员三个固定角色。

## 3. 目标与非目标

### 3.1 目标

1. 建立可信的服务端租户上下文，确保任何页面、接口、后台任务和 Provider 请求都不能跨租户访问数据。
2. 建立平台管理后台，用于管理租户、套餐、有效期、Provider 节点额度和租户管理员。
3. 建立租户员工与固定角色权限体系，支持账号禁用、密码修改和角色变更后的会话即时失效。
4. 建立 Provider 节点管理与一次性激活流程，使客户电脑只需主动访问云端 HTTPS，不需要公网 IP 或开放入站端口。
5. 将现有企业微信渠道、联系人、群聊、消息、任务和插件能力纳入租户范围。
6. 引入 Alembic，停止继续依赖启动时 `create_all` 和运行时临时补列作为正式生产升级方式。
7. 提供旧系统数据导入工具，将历史数据安全归入指定租户。

### 3.2 非目标

- 首期不提供公众注册、短信验证、在线支付、自动续费或发票能力。
- 首期不提供自定义角色和权限编辑器。
- 首期不按员工数、渠道数、消息量或调用量计费。
- 首期不重写 Vue 3 前端。
- 首期不删除微信、Telegram、OpenClaw 等旧渠道适配器源码。
- 首期不采用租户独立数据库、租户独立容器或客户独立部署的模式。
- 首期不使用 WebSocket 作为 Provider 必需链路；低延迟推送可作为后续增强。

## 4. 方案比较与结论

### 4.1 统一租户上下文和全业务表租户字段

所有租户业务表显式保存 `tenant_id`，认证层创建可信租户上下文，查询和写入通过租户感知的服务统一执行。后台任务、Webhook、Provider 和开放接口都从已验证凭证推导租户。

优点是隔离规则明确、查询效率可控、适合当前 MariaDB 和单体架构，也便于后续拆分服务。缺点是需要系统性改造现有模型、查询、唯一约束和测试。

### 4.2 在页面和接口中临时追加过滤条件

该方案改造较快，但容易遗漏后台 Worker、定时任务、Webhook、Provider 回调和开放接口。一旦遗漏，就可能产生跨租户读取或写入，因此不采用。

### 4.3 每租户独立数据库

该方案隔离强，但会显著增加建库、迁移、备份和运维成本，也不符合已确认的共享 SaaS 模式，因此不采用。

### 4.4 结论

采用方案 4.1：共享 MariaDB、全业务表显式 `tenant_id`、统一租户上下文和服务端强制隔离。

## 5. 总体架构

```text
平台管理员后台
      │ 创建租户、套餐、有效期、节点额度
      ▼
Multi Bot SaaS 云端
├── 平台身份认证与平台管理
├── 租户身份认证与员工权限
├── 企业微信渠道与 Provider 节点管理
├── 联系人、群聊、会话、消息和插件
├── 任务队列、运行监控和审计
└── MariaDB 共享数据库，业务数据按 tenant_id 隔离
      ▲
      │ HTTPS 激活、心跳、长轮询、任务回报、事件上传
      │
客户 Windows PC
└── 企业微信 Provider
    └── 一台电脑一个节点，一个节点可承载多个企微账号
```

云端是控制面和数据面入口。Provider 只建立出站 HTTPS 连接，不要求客户网络提供可被云端访问的端口。

## 6. 身份、会话与权限

### 6.1 平台身份

平台管理员账号与租户员工账号使用独立的数据范围和登录入口。平台管理员可以：

- 创建、启用、停用租户；
- 设置套餐、有效期和 Provider 节点额度；
- 创建或重置租户管理员；
- 查看租户级资源用量、Provider 在线状态和平台审计记录；
- 进入受审计的租户支持视图，但不能依靠伪造 `tenant_id` 访问租户接口。

平台管理员不属于普通租户角色体系。

### 6.2 租户员工

首期固定三个角色：

- `tenant_admin`：员工、Provider、企微渠道、机器人、插件和全部租户业务管理；
- `operator`：机器人、企微渠道、联系人、群聊、会话、任务和插件配置管理；
- `readonly`：只查看业务数据、运行状态和日志。

所有修改类路由继续由后端强制鉴权，页面隐藏按钮只作为交互提示，不能替代权限检查。

### 6.3 数据库会话

租户登录改为数据库会话：

- Cookie 只保存随机会话标识，不直接信任 Cookie 中的用户名、角色或租户编号；
- 数据库只保存会话令牌摘要；
- 每个受保护请求重新校验账号状态、租户状态、角色和会话版本；
- 禁用员工、修改密码、调整角色或停用租户后，现有会话立即失效；
- Cookie 在生产环境启用 `HttpOnly`、`Secure` 和合适的 `SameSite` 策略。

密码使用 Argon2id 等专用密码哈希算法，不继续使用普通 SHA-256 拼接密钥的方式。

## 7. 租户上下文与隔离规则

### 7.1 上下文来源

- 租户页面和内部接口：从已验证的租户会话获得 `tenant_id`；
- Provider 接口：从设备密钥获得 `tenant_id` 和 `provider_node_id`；
- Webhook：从渠道密钥反查渠道，再获得 `tenant_id`；
- 开放 API：从应用密钥反查开放应用，再获得 `tenant_id`；
- 后台任务：任务创建时固化 `tenant_id`，Worker 执行时再次校验任务与资源归属；
- 平台管理接口：使用平台权限，并显式记录被管理的目标租户和审计信息。

普通客户端提交的 `tenant_id` 永远不能作为可信归属依据。

### 7.2 查询规则

- 读取单条资源时同时按 `id` 和 `tenant_id` 查询；
- 列表、统计、搜索、导出和监控查询必须包含租户过滤；
- 创建子资源前校验所有父资源属于当前租户；
- 更新和删除语句必须同时限定主键和租户；
- 批量操作必须先验证输入 ID 集合全部属于当前租户；
- 找不到资源与资源属于其他租户时统一返回 `404`，避免泄露资源存在性。

### 7.3 防止遗漏

业务代码通过统一的租户上下文、依赖函数和租户感知服务访问数据。禁止在新租户路由中直接执行没有租户条件的业务模型查询。代码评审和测试需要搜索并审计所有业务查询入口。

## 8. 数据模型

### 8.1 平台与租户表

- `platform_users`：平台管理员账号；
- `platform_sessions`：平台管理员数据库会话和失效状态；
- `tenants`：租户编码、名称、状态和基础信息；
- `saas_plans`：套餐名称、Provider 节点上限和启停状态；
- `tenant_subscriptions`：租户套餐、有效期、订阅状态和人工备注；
- `tenant_users`：租户员工账号；
- `tenant_sessions`：租户数据库会话和失效状态；
- `platform_audit_logs`：平台级管理审计。

现有 `audit_logs` 增加 `tenant_id` 后继续承担租户内操作审计，避免再维护一套重复的租户审计表。

首期一个员工账号只属于一个租户，因此可直接在 `tenant_users` 保存 `tenant_id` 和固定角色。若未来需要一个账号加入多个租户，再迁移为全局用户和成员关系表，不在首期提前增加复杂度。

### 8.2 Provider 表

- `provider_nodes`：节点名称、租户、设备指纹、版本、状态、最后心跳和停用信息；
- `provider_node_accounts`：节点发现的企业微信账号标识、展示信息、在线状态和最后上报时间；
- `provider_activation_codes`：一次性激活码摘要、有效期、消费状态和创建人；
- `provider_credentials`：设备密钥摘要、版本、吊销状态和最后使用时间；
- `provider_heartbeats`：必要的节点状态快照；高频历史采用保留策略，避免无限增长。

### 8.3 业务表

下列数据按租户归属：

- 机器人、机器人分组、标签、配置模板；
- 企业微信渠道、Provider 绑定；
- 企业微信联系人、联系人关系、群聊和群成员；
- 会话、消息、附件、原始 Webhook 事件；
- 插件绑定、群插件范围、插件执行记录；
- 客户运营请求、开放 API 应用和授权渠道；
- 任务、错误日志、健康记录、告警、统计和审计记录；
- 积分、签到等仍被保留的插件业务数据。

插件目录中由代码扫描得到的插件定义属于平台共享目录；租户自己的启停、绑定和配置必须保存在带 `tenant_id` 的关联表中。

### 8.4 约束与索引

- 所有租户业务表为 `tenant_id` 建立索引；
- 名称、编码、外部事件编号和幂等编号改为租户内唯一；
- 高风险父子关系使用租户一致性校验，必要时建立包含 `tenant_id` 的复合约束；
- Provider 节点与企微渠道的绑定必须属于同一租户；
- 一个企微渠道只能绑定一个有效 Provider 节点；
- 一个 Provider 节点可以绑定多个企微渠道。

## 9. 套餐与有效期

首期套餐只控制 `provider_node_limit`。

### 9.1 节点额度

- 额度按租户中未删除且已激活的 Provider 节点计数；
- 创建待激活节点时预占额度，避免并发超卖；
- 达到上限后禁止创建或激活新节点，返回明确错误；
- 平台降低额度且当前节点数超过新上限时，不强制踢掉已有节点，但禁止继续新增，平台界面显示超额状态；
- 停用或删除节点后释放额度。

### 9.2 租户到期

- 租户员工仍可登录只读查看历史数据和到期提示；
- 禁止新增或修改员工、Provider、渠道和业务配置；
- Provider 仍可上报心跳，但不能领取新发送任务；
- 已领取任务允许在租约期内完成回报，避免出现状态悬空；
- 入站事件可按配置继续接收并标记受限，首期默认接收，以避免客户历史记录丢失；
- 平台续期后恢复正常运行，不需要重新激活 Provider。

## 10. Provider 节点生命周期

### 10.1 创建与激活

1. 租户管理员创建 Provider 节点，系统原子校验节点额度。
2. 云端生成高熵一次性激活码，只向管理员展示一次；数据库保存摘要。
3. 激活码默认 30 分钟失效，未消费前允许管理员主动撤销和重新生成。
4. 客户在 Windows Provider 中填写 SaaS 地址和激活码。
5. Provider 发送节点名称、客户端版本和稳定设备指纹摘要。
6. 云端验证租户状态、额度、激活码状态和节点状态。
7. 激活成功后，云端原子标记激活码已消费，并返回只展示一次的设备密钥。
8. Provider 将设备密钥写入本机受限配置文件，后续不再使用激活码。

### 10.2 日常连接

首期采用 HTTPS 心跳和长轮询：

- Provider 定期上报客户端版本、Hook 状态、企微进程状态和当前账号摘要；
- 每个账号摘要包含节点内稳定的 `account_key`，云端据此维护节点账号，不信任客户端修改其租户归属；
- Provider 使用长轮询领取属于该节点的待处理任务；
- 云端响应中可以包含配置版本和凭证轮换提示；
- 网络超时按正常空轮询处理，客户端使用带抖动的指数退避重试；
- 后续如需更低延迟，可增加 WebSocket 通知，但 HTTP 长轮询继续作为恢复链路。

### 10.3 禁用、解绑和密钥轮换

- 禁用节点后，设备密钥立即不能领取任务或上传业务事件；
- 解绑节点前需要确认其没有正在执行的任务；
- 管理员可吊销旧密钥并生成新的短期重新激活码；
- 所有激活、吊销、解绑和轮换操作进入审计日志；
- 设备密钥、激活码和渠道密钥不得出现在普通日志或页面回显中。

## 11. 企业微信渠道绑定

- 租户后台只展示和允许创建 `workwechat` 渠道；
- 创建渠道时必须选择本租户中已激活且可用的 Provider 节点及其已发现账号；
- 同一节点可绑定多个企微渠道；
- Provider 心跳上报本机可识别的企微账号，租户管理员完成节点账号与云端渠道的绑定；
- 一个企微渠道只能绑定一个节点账号，同一个节点账号首期只允许绑定一个有效企微渠道；
- Provider 拉取任务时只能获得绑定到自身节点的渠道任务；
- Provider 回报任务或上传事件时，云端同时校验租户、节点、渠道和任务四者关系；
- 其他渠道的创建入口和导航在 SaaS 租户后台中隐藏，服务端同样拒绝租户创建非 `workwechat` 渠道。

## 12. 核心数据流

### 12.1 租户开通

1. 平台管理员创建租户并选择套餐、有效期。
2. 平台创建首个租户管理员，系统生成一次性初始密码或密码设置链接。
3. 租户管理员首次登录后必须修改密码。
4. 租户管理员继续创建运营和只读员工。

### 12.2 出站任务

1. 租户员工、插件或开放 API 创建发送任务。
2. 云端从可信上下文确定 `tenant_id`，校验渠道和 Provider 节点归属。
3. 任务保存 `tenant_id`、`channel_id`、`provider_node_id`、`provider_account_id` 和幂等键。
4. Provider 长轮询领取任务，云端创建带过期时间的任务租约。
5. Provider 本地执行企业微信发送，并使用本地幂等记录防止重复发送。
6. Provider 携带任务租约令牌回报成功或失败。
7. 云端幂等更新任务、消息和业务请求状态。

### 12.3 入站事件

1. Provider 使用设备密钥上传企业微信事件。
2. 云端从凭证确定租户和节点，再校验事件中的渠道属于该节点。
3. 以租户、渠道和外部事件编号组成幂等边界。
4. 联系人、群聊、会话、消息和插件任务全部继承同一 `tenant_id`。

### 12.4 后台任务

后台 Worker 领取任务后，必须使用任务自己的 `tenant_id` 加载渠道、会话和插件绑定。资源不存在、租户不一致、租户停用或任务租约不合法时，不执行外部发送，并记录租户级错误。

## 13. 错误处理与幂等

### 13.1 标准错误

- `tenant_not_found`：租户不存在；
- `tenant_disabled`：租户已停用；
- `tenant_expired`：租户已到期且当前操作不可执行；
- `provider_node_limit_reached`：Provider 节点额度已满；
- `activation_code_invalid`：激活码无效、过期、撤销或已使用；
- `provider_credential_invalid`：设备凭证无效或已吊销；
- `provider_node_disabled`：节点已禁用；
- `resource_not_found`：资源不存在或不属于当前租户；
- `job_lease_conflict`：任务已被其他轮询领取或租约已失效；
- `duplicate_event`：事件已经处理。

页面显示可操作的中文提示，接口返回稳定错误码和请求追踪编号。内部异常信息、SQL、密钥和其他租户标识不得返回客户端。

### 13.2 并发与幂等

- 节点额度检查和节点创建必须处于同一数据库事务；
- 激活码消费使用条件更新或行锁，确保只能成功一次；
- Provider 任务领取使用租约和条件更新，确保同一时刻只有一个节点实例获得任务；
- 完成和失败回报按任务编号、租约令牌和结果幂等键处理；
- 入站事件使用租户级复合唯一约束去重；
- 网络超时不能直接推断发送失败，Provider 需先查询或恢复本地任务状态，避免重复发送。

## 14. 安全设计

- 所有生产 Provider 通信必须使用 HTTPS；
- 密码使用 Argon2id，设备密钥、激活码、开放 API 密钥只保存摘要；
- 登录、激活、轮询失败和密钥校验接口实施速率限制；
- Jinja 表单增加 CSRF 防护；
- 敏感字段在页面、日志、审计元数据和异常中统一脱敏；
- 平台管理员查看租户支持信息需要显式操作并记录审计；
- 任何跨租户资源猜测统一返回 `404`；
- 文件上传路径按租户分区，下载前再次校验租户归属；
- 导出、统计和缓存键必须包含租户编号；
- 定时清理过期激活码、吊销凭证、过期会话和过量心跳历史。

## 15. 页面范围

### 15.1 平台后台

- 平台登录；
- 租户列表、创建、详情、启停；
- 套餐管理；
- 租户订阅、有效期和 Provider 节点额度调整；
- 租户管理员创建或重置；
- 全平台 Provider 在线概览；
- 平台审计日志。

### 15.2 租户后台

- 租户登录和首次修改密码；
- 当前租户、套餐、有效期和节点用量展示；
- 员工列表、创建、角色调整和启停；
- Provider 节点列表、创建、激活码、禁用、解绑和状态详情；
- 企业微信渠道与 Provider 节点绑定；
- 复用并租户化现有机器人、联系人、群聊、会话、消息、插件、任务和监控页面；
- 隐藏其他渠道入口和无关设置。

页面继续沿用现有紧凑型后台视觉语言，避免在首期进行大范围视觉重构。

## 16. 数据迁移

### 16.1 新项目数据库

新项目建立 Alembic 基线和连续迁移。应用启动只检查数据库版本，不再自动执行不可追踪的生产补列。

### 16.2 旧数据导入

提供显式命令行迁移工具：

1. 校验来源数据库只读连接和目标数据库结构版本；
2. 在目标库创建或选择“自营租户”；
3. 按依赖顺序导入机器人、渠道、联系人、群聊、会话、消息、任务和日志；
4. 建立旧 ID 到新 ID 的映射，不能假设目标主键为空；
5. 对密钥和密码执行兼容迁移或强制轮换；
6. 输出逐表数量、跳过项和错误报告；
7. 支持校验模式和正式执行模式；
8. 正式导入前备份目标数据库，导入失败时事务回滚或按批次可恢复。

旧 `multi-bot-admin` 数据库和服务在验收完成前不做原地修改。

## 17. 测试与验收

### 17.1 自动化测试

- 租户、套餐、员工、会话和 Provider 节点模型测试；
- 三种租户角色的路由权限测试；
- 两个租户使用相同名称、外部 ID 和幂等编号时互不冲突；
- 使用甲租户会话访问乙租户资源 ID 时始终返回 `404`；
- 列表、搜索、统计、导出和监控不包含其他租户数据；
- Provider 激活码一次性、过期、撤销和并发消费测试；
- Provider 节点额度并发校验测试；
- 禁用节点、吊销密钥和租户到期后的行为测试；
- 任务领取租约、超时恢复、重复回报和重复事件测试；
- 企业微信渠道只能绑定本租户节点的测试；
- Webhook、开放 API、后台 Worker 和插件链路的租户传播测试；
- 旧数据迁移的数量、关系和租户归属校验测试；
- 保留并适配当前企业微信业务回归测试。

### 17.2 安全验收

建立专门的跨租户攻击测试矩阵，覆盖 URL 主键替换、表单字段篡改、批量 ID 混入、Provider 渠道伪造、开放 API 应用越权、文件下载猜测和任务回报伪造。

### 17.3 运行验收

- 本地完整测试通过；
- Alembic 在空库升级、旧版本升级和降级边界验证通过；
- Docker 镜像和 Compose 启动通过；
- 平台管理员可以创建租户和套餐；
- 租户管理员可以创建员工和激活 Provider；
- Windows Provider 可以完成激活、心跳、任务领取和结果回报；
- 两个测试租户并行运行时数据严格隔离；
- 备份、迁移演练、健康检查和日志脱敏通过。

## 18. 项目与部署策略

- 新目录：`/data/multi-bot-saas`；
- 新 Git 仓库：`multi-bot-saas`；
- 复制代码时排除 `.git`、虚拟环境、本地 `.env`、数据库、日志、缓存和运行态文件；
- 开发期间只提交新项目文件，不改动或覆盖现有项目中的用户未提交变更；
- 每个实现阶段完成后按仓库要求使用中文提交信息；
- 新服务使用独立容器名、数据库名、卷和端口，避免与现有 `multi-bot-admin` 冲突；
- 部署前先完成数据库备份和配置核对；
- 远程部署采用新仓库 `git pull`、Alembic 升级、重建或重启服务、健康检查和双租户隔离验收；
- 正式切换前，现有生产项目继续独立运行，作为可回退系统。

## 19. 实施顺序

1. 安全复制项目并建立独立 Git 仓库；
2. 建立 Alembic 基线、平台/租户身份和数据库会话；
3. 建立统一租户上下文与授权依赖；
4. 为核心业务模型、约束和服务增加租户归属；
5. 改造企业微信 Provider 节点、激活和长轮询协议；
6. 改造后台任务、Webhook、开放 API、插件和文件链路；
7. 建立平台后台、租户员工和 Provider 管理页面；
8. 隐藏并服务端禁用非企业微信渠道；
9. 完成旧数据迁移工具；
10. 执行自动化、安全、Docker、Windows Provider 和双租户验收；
11. 创建远程仓库并按独立部署配置发布。

## 20. 完成标准

只有同时满足以下条件，才视为 SaaS 改造完成：

- 平台、租户、员工、套餐和 Provider 节点工作流完整可用；
- 所有租户业务入口均有服务端租户隔离，跨租户测试全部通过；
- 企业微信 Provider 无需客户开放公网端口即可稳定运行；
- 节点额度、租户到期、禁用、密钥吊销和任务恢复行为符合设计；
- Alembic、备份、迁移和回滚路径经过验证；
- 现有企业微信核心功能没有回归；
- 新项目、数据库和部署不影响现有 `multi-bot-admin`；
- 代码包含必要的详细中文注释，并按阶段形成清晰的中文 Git 提交记录。
