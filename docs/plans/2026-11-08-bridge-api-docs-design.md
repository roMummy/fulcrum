# 桥接接口文档中心设计

## 背景

曜枢 AI 当前的插件主要用于展示业务能力，但外部用户后续应当能够脱离插件，直接通过桥接接口开发自己的订单、客服、通知、收发单和自动化业务。现有接口已经具备消息发送、文件发送、会话查询、群查询、任务状态查询和事件回调能力，缺少一个登录后可访问、面向开发者连续说明这些能力的文档中心。

本次只建设接口文档展示，不新增登录接口、扫码登录接口、代理连接器接口或业务能力接口。用户的微信登录、渠道接入和代理配置仍由平台后台完成；第三方业务系统只使用已经授权的渠道和会话。

## 目标与边界

目标是让已经登录企业工作台的用户可以：

1. 了解桥接接口的整体调用流程和资源关系。
2. 按文档完成签名鉴权、查询群和会话、发送文本或文件、查询任务状态。
3. 配置接收消息和发送结果的 Webhook，并在自己的系统内维护业务状态。
4. 理解幂等、分页、错误码和渠道授权边界，避免把平台内部数据库字段当成稳定协议。

本次明确不做：

- 不开放或说明微信扫码登录、874 协议和 Windows 本地代理连接器的实现细节。
- 不新增开放应用管理 API，不改变现有 `OpenApiApp` 的创建和授权方式。
- 不把后台登录 Cookie 作为第三方业务系统的调用凭证。
- 不把 `/api/tool/*` 提升为新项目的推荐协议；它只作为兼容工具接口保留说明。
- 不自动从 Python 类型或 OpenAPI schema 生成整套页面，避免把内部字段直接暴露成公共协议。

## 推荐方案

采用“Markdown 内容源 + 登录后文档页面”的组合：

- `docs/bridge-api.md` 是唯一的文档内容源，进入 Git 版本管理，便于代码审查和后续维护。
- 新增租户认证后的 `/developer/docs` 页面，服务端读取 Markdown 并渲染为安全 HTML。
- 企业工作台主导航增加“开发文档”入口，所有已登录租户员工可阅读；文档中的密钥、应用和渠道授权操作仍由现有权限页面负责。
- 页面沿用现有工作台布局、导航、登录态和视觉令牌，不新建独立后台壳。

相比只放仓库 Markdown，这种方式能让实际使用产品的开发者在同一工作台内直接阅读；相比把大量内容写进 Jinja 模板，Markdown 能保持内容与页面结构分离，后续新增接口章节不会重复修改 HTML。

## 文档内容结构

`docs/bridge-api.md` 按以下顺序组织：

1. **定位与快速开始**：说明桥接层负责消息和业务数据交换，业务系统自行维护订单、状态和重试；给出最小调用链。
2. **前置条件**：说明渠道、开放应用、授权渠道和会话数据必须先由平台配置；文档不包含账号扫码登录流程。
3. **鉴权**：说明 `X-App-Key`、`X-Timestamp`、`X-Signature` 和可选 `X-Tenant-Code`，签名内容固定为 `timestamp + "\\n" + 原始请求体`，算法为 HMAC-SHA256；GET 请求使用空请求体参与签名。
4. **资源概念**：说明 `channel_id`、`conversation_external_id`、`chat_type`、`request_id` 和任务状态，强调外部系统保存自己的业务主键。
5. **读取接口**：`GET /api/open/chatrooms`、`GET /api/open/conversations` 和 `GET /api/open/jobs/{request_id}`。
6. **发送接口**：`POST /api/open/messages` 支持文本、图片、链接和小程序；`POST /api/open/files` 支持文件上传或已存在文件路径/URL的统一任务入口。
7. **Webhook**：说明入站消息和开放接口发送结果的事件信封、签名校验、异步投递和重试边界；业务系统必须按 `event_id` 或 `request_id` 做幂等。
8. **错误和幂等**：列出鉴权失败、渠道未授权、参数错误、任务失败等稳定错误；说明同一 `request_id` 重试会返回原任务。
9. **兼容工具接口**：简要指向 `/api/tool/channels/{channel_id}/messages`、`/api/tool/channels/{channel_id}/upload-and-send` 和 `/api/tool/jobs/{job_id}`，说明其全局 `X-API-Key + X-Tenant-Code` 模式只适合已有内部工具。
10. **业务实现建议**：给出订单收发、客服机器人和通知系统的最小架构示例，明确平台只做渠道桥接，业务规则由用户自己的系统负责。

每个推荐接口都包含：HTTP 方法和路径、请求头、请求参数、成功响应、失败响应、curl 示例和 Python 示例。示例中的地址、密钥、租户编码和 ID 全部使用占位符，不写入真实部署信息。

## 页面与路由

新增 `app/web/developer_docs.py`：

- 使用现有租户身份恢复逻辑校验登录态，未登录跳转 `/login`。
- 只允许读取文档文件，不接受用户提交内容。
- 读取固定路径 `docs/bridge-api.md`，禁止使用请求参数拼接文件路径。
- 使用 Python Markdown 库启用 `extra` 和 `codehilite`，输出交给 Jinja 自动转义后的安全页面；代码块使用现有静态样式扩展。
- 页面上下文复用 `build_tenant_navigation`，让“开发文档”在当前路径下保持激活态。

新增 `app/templates/developer_docs.html`：

- 继承 `base.html`，显示页面标题、适用范围和文档正文。
- 在正文顶部放置“推荐接口 / 兼容工具接口”的定位提示。
- 不显示应用密钥、渠道密钥、登录二维码或本地代理凭证。

更新 `app/main.py` 注册开发文档 Router，更新 `app/web/tenant_navigation.py` 增加“开发文档”入口。样式只补充文档排版所需的标题、代码块、表格和响应式滚动，不改变现有业务组件。

## 数据流

```text
企业用户登录工作台
        |
        v
开发文档页面 /developer/docs
        |
        v
阅读 docs/bridge-api.md
        |
        v
用户自己的业务系统 -- HMAC --> /api/open/*
        |
        +--> 查询已授权群/会话
        +--> 创建异步发送任务
        +--> 查询任务状态
        +<-- 接收消息/发送结果 Webhook
```

文档页面本身不参与业务 API 鉴权。业务 API 使用用户在开放应用配置中获得的 `app_key` 和 `app_secret`，服务端继续根据开放应用授权渠道恢复租户边界。

## 错误处理与安全边界

- Markdown 只能从仓库内固定文件读取，文件不存在或解析失败时返回稳定的服务错误页面，不把路径和异常堆栈回显给用户。
- 页面不渲染任何运行时密钥和租户敏感配置。
- 文档中的 HMAC 示例必须对原始请求体签名，不能先格式化 JSON 后再发送另一份请求体。
- 所有异步发送接口都要求业务方提供稳定 `request_id`，重试时复用该值。
- Webhook 说明必须强调服务端异步投递，业务方需要校验时间戳、签名和事件幂等，不能把 HTTP 200 当作业务处理完成的唯一依据。

## 验证

本次实现完成后执行以下轻量验证：

1. 文档页面未登录访问会跳转 `/login`，已登录访问返回 `200`。
2. 页面包含关键章节、推荐接口路径和代码块，且不包含真实密钥或部署密码。
3. 现有开放接口定向测试继续通过。
4. 文档 Markdown 解析、路由注册和模板语法通过定向测试或语法检查。
5. `git diff --check` 通过。
