# 租户双向 Webhook 能力设计草案

> 状态：暂停，等待后续继续确认。本文只归档已经讨论的需求、现状和设计约束，不代表已经批准实施。

## 背景

当前平台允许企业使用平台内置插件处理 Channel 消息，也已经存在外部系统主动调用平台发送消息的 Open API，以及面向特定收发单业务的 Webhook 投递代码。但是现有能力没有形成租户可以自行配置、观察和维护的通用产品功能，无法作为 SaaS 的标准扩展入口交付。

目标是让企业在不安装平台插件、不接触 Provider 或协议服务内部配置的情况下，把自己的业务系统连接到一个明确授权的 Channel，并完成双向消息流转。

## 已确认需求

### 双向消息能力

1. Channel 收到消息后，平台把标准化消息事件异步推送到企业配置的 Webhook 地址。
2. 企业系统可以通过平台提供的入站发送接口，向已绑定 Channel 中的目标会话发送消息。
3. 入站发送既支持回复刚收到的事件，也支持向历史会话主动发送消息。
4. 发送动作进入平台任务队列，不允许外部请求同步调用具体渠道协议或 Provider。
5. 发送成功或失败应继续通过标准事件通知外部系统，便于外部系统维护自己的业务状态。

### Channel 授权边界

1. 每个 Webhook 集成显式绑定一个 Channel。
2. 新建集成默认没有其他 Channel 权限，不能自动获得当前租户全部 Channel。
3. 外部请求中的租户 ID、Channel ID 或其他数据库主键不能作为可信权限来源。
4. 平台必须从已经认证的集成凭据反查租户和唯一绑定 Channel。

### 会话定位

1. 出站事件提供稳定且不暴露内部租户、Channel 主键的 `conversation_ref`。
2. 外部系统可以使用 `conversation_ref` 回复当前消息或向历史会话主动发送。
3. 回复场景可以同时携带 `reply_to_event_id`，用于审计消息与原始事件的关联关系。
4. 平台负责把 `conversation_ref` 解析为当前集成有权访问的真实会话，禁止跨 Channel 使用。

### 插件协作模式

每个集成支持以下两种处理模式：

- 协同模式：Webhook 与平台业务插件都可以处理同一条消息，作为默认模式。
- 外部接管模式：消息继续落库、统计和审计，但不再触发普通业务插件，避免平台插件与外部系统重复回复。

系统级消息标准化、附件处理、安全审计和运行统计不受接管模式影响。

## 当前代码基础

当前仓库已经具备以下可复用能力：

- `OpenApiApp` 和 `OpenApiAppChannel`：保存机器应用身份和授权渠道。
- Open API HMAC 请求签名：校验应用密钥、时间戳和请求正文。
- `TaskJob`：支持异步任务、失败重试、可用时间和租户归属。
- `RawWebhookEvent`、`Message` 和 `MessageAttachment`：保存标准化入站事件、消息和附件。
- `open_webhooks.py`：可以异步投递 `message.received`、`file.received`、`message.sent` 和 `message.failed`。
- 租户上下文和租户会话：后台任务可以在可信租户范围内读取和写入业务数据。

现有 Webhook 实现主要服务特定收发单系统，尚不能直接作为通用 SaaS 功能交付。

## 当前实现缺口

1. 没有企业租户自助创建、停用、测试或查看 Webhook 集成的产品入口。
2. `webhook_url` 和 `webhook_secret` 仍附着在 Open API 应用字段上，职责混合，无法支持独立订阅和密钥轮换。
3. Webhook Secret 没有使用平台敏感配置加密能力保存。
4. 没有通用事件订阅模型，部分过滤仍依赖特定 `app_key` 的硬编码判断。
5. 没有完整的目标地址校验、SSRF 防护、DNS 重绑定防护和跳转地址复核。
6. Webhook 投递与其他后台任务共用单一 Worker，慢接口可能阻塞插件和消息发送任务。
7. 没有独立投递记录、响应摘要、下次重试时间、人工重试和暂停原因。
8. 固定重试次数和固定延迟不足以应对外部系统故障，也缺少熔断和自动暂停。
9. 附件事件可能暴露宿主机 `storage_path`，通用协议只能提供受控下载地址和必要元数据。
10. 缺少租户级调用频率、并发数、消息体大小和每日事件数量限制。

## 推荐数据边界

后续继续设计时，建议把 Webhook 从 `OpenApiApp` 的附属字段拆成独立资源：

- Webhook 集成：租户、名称、唯一绑定 Channel、处理模式、状态和公开凭据标识。
- Webhook 端点：目标 URL、加密 Secret、签名版本和目标地址校验状态。
- 事件订阅：允许接收的标准事件类型。
- Webhook 事件：平台生成的稳定事件 ID、事件类型、租户和 Channel 归属、标准化载荷摘要。
- 投递记录：每次尝试、HTTP 状态、耗时、错误类别、下次重试时间和终态。
- 入站发送请求：外部 `request_id`、`conversation_ref`、消息类型、任务状态和幂等结果。

以上表均需要显式保存 `tenant_id`，Worker 领取任务后必须重新建立对应租户上下文。

## 安全约束

### 身份与签名

1. 每个集成生成独立的公开 Key 和 Secret，Secret 只展示一次并加密保存。
2. 请求签名至少覆盖签名版本、时间戳、请求 ID、HTTP 方法、路径和原始正文摘要。
3. 入站请求必须校验时间窗口和请求 ID，防止重放。
4. Secret 轮换需要提供短时间双密钥窗口，但不得保留永久兼容分支。
5. 所有鉴权失败只返回稳定错误码，不泄露租户、Channel 或会话是否存在。

### 目标地址安全

尚未最终确认的推荐策略：租户只能配置公网 HTTPS 地址；平台管理员可以为测试环境或私有部署维护明确的内网地址白名单。

目标地址校验至少需要覆盖：

- 禁止 URL 中携带用户名和密码。
- 禁止环回、链路本地、云元数据、组播和未授权私网地址。
- 创建和每次投递前都解析 DNS，并复核最终连接地址。
- 禁止自动跟随到未授权地址，或对每次跳转重新执行完整校验。
- 限制端口范围、响应头大小和响应体读取量。
- 生产环境默认只允许 TLS，并校验证书。

### 数据最小化

1. Webhook 只发送标准化业务字段，不发送原始 Provider 回包、协议凭据、代理信息和内部配置。
2. 附件使用短期签名下载 URL，不发送宿主机路径。
3. 消息内容、附件名称和外部用户信息需要进入日志脱敏规则。
4. 管理页面只显示 Secret 指纹、目标域名和最近投递摘要，不回显 Secret。

## 性能约束

1. Channel 入站事务只负责消息落库和创建 Webhook 事件，不同步等待客户接口。
2. Webhook 使用独立任务类型和独立 Worker 并发池，不能阻塞插件、协议轮询和消息发送。
3. 同一集成默认按事件顺序投递，不同集成可以并行。
4. 单次连接、首字节和总请求时间分别设置上限，总超时不应沿用当前固定 10 秒等待方式。
5. 使用指数退避和随机抖动，明确区分可重试错误与永久失败。
6. 连续失败达到阈值后自动熔断，暂停新投递并通知企业管理员。
7. 限制单事件载荷、单租户队列长度、每秒投递数和最大并发数。
8. 投递记录与大载荷分离保存，按保留周期归档或清理，避免主业务表持续膨胀。

## 暂定事件流

### Channel 消息推送

1. 渠道消息进入现有标准化入站链路。
2. 平台完成去重、消息落库和附件状态处理。
3. 根据唯一绑定 Channel 查找启用的 Webhook 集成。
4. 在同一数据库事务内创建标准事件和待投递记录。
5. Webhook Worker 异步签名并投递。
6. 外部系统按 `event_id` 幂等消费并返回任意 `2xx`。
7. 平台记录耗时和结果，失败时按策略重试或熔断。

### 外部系统发送消息

1. 外部系统提交签名请求、唯一 `request_id`、`conversation_ref` 和消息内容。
2. 平台从集成凭据反查租户和唯一 Channel。
3. 平台校验 `conversation_ref`、消息类型、载荷大小、速率和 Channel 能力。
4. 相同 `request_id` 返回原任务结果，不重复发送。
5. 平台创建现有消息发送任务并立即返回 `202`。
6. 任务完成后产生 `message.sent` 或 `message.failed` 事件。

## 未决问题

1. 是否最终采用“公网 HTTPS 加平台内网白名单”的目标地址策略。
2. 首版允许订阅哪些事件，是否把文件就绪作为独立事件。
3. 首版入站发送支持哪些消息类型，是否先限制为文本、图片、文件和链接。
4. 是否允许一个 Channel 同时绑定多个 Webhook 集成，当前讨论倾向一个集成绑定一个 Channel，但尚未确认 Channel 侧唯一性。
5. 投递重试次数、退避周期、熔断阈值和记录保留天数。
6. 免费试用和付费套餐分别提供多少事件额度、并发数和每日发送量。
7. 企业管理员页面需要提供哪些测试、重放、日志下载和告警能力。
