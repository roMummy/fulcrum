# 微桥邀请资料接入图谱设计

## 目标与授权

沿用用户已确认的邀请关系图谱、成员身份排序与后台风格，执行本轮“帮我完善这个图谱”的要求。结合 2026-11-15 在 201 的实际调用结果，补齐邀请资料读取、持久化、进度与时间语义，完成轻量验证后部署到用户已指定的 201。不重复询问已确认的交互方案。

## 接口依据

渠道 2 的微桥 8.0.80-23 已报告 `room_member_join_info` 能力。该命令必须逐成员传入 `room_id`、`wxid`，本轮使用 `refresh: true`。三个成功样例均为 `status: partial`，包含有效 `inviter_wxid`、`inviter_name` 与 `join_description`，而 `join_time: null`。`partial` 不等于失败；不能把查询、任务完成或同步时刻当作真实入群时间，也不能从描述反推未知的 `join_type`。

## 方案选择

采用用户主动发起、后台小批量执行的独立“同步邀请关系”，保留历史系统消息补查。相比打开页面就自动逐成员请求，主动同步可控制手机查询量；相比一次入队整个大群，小批量任务更易恢复且不挤占消息队列。现有图谱的头像卡片、搜索、缩放、分支展开和放大弹窗继续使用。

## 数据与流程

1. 邀请证据仍只有成员 `extra_json.invitation` 一份。新增“微桥入群资料”来源，优先使用明确 ID；昵称仅展示。新接口支持未知邀请人的资料快照，只有有效邀请人才能生成边。
2. 保存接口实际返回的入群时间、入群说明，以及独立的资料获取时间；证据顺序以请求开始时间比较。失败、错配、旧回报及缺失邀请人不能抹掉已有有效关系。
3. 群 `extra_json.invitation_sync` 保存本轮代次、主键游标、成员上界、少量在途任务与计数，不新增数据库表。仅查询当前在群成员；退出群成员的历史关系继续展示。本轮开始后新加入的成员留待下一轮。
4. 每批最多 3 个查询，低于业务消息优先级；同群重复点击复用在途同步。回报后续排，手机轮询维护负责超时结算和进程重启后的恢复，不依赖页面持续打开。同步结束后可重新同步，失败不自动无限重试。
5. 回报必须匹配已保存命令中的租户、渠道、群和成员；同步代次过期不写入。状态 GET 与普通页面 GET 均只读，不自动下发命令。
6. 新来源优先于通用成员资料和系统消息；只有已知邀请人触发来源优先保护，未知快照不能阻止后续有效系统证据。

## 页面与错误

仅有运营权限的用户能启动同步，POST 校验 CSRF 和租户归属。能力不支持时显示原因，不偷偷改用无关接口。成员页显示进度、查到邀请人的人数、未知与失败计数；完成或已有新结果时提供“更新图谱”。节点详情显示邀请人、来源、入群时间、资料获取/证据记录时间、接口说明和直接邀请数。时间缺失显示“未知”，文本继续自动转义。

## 验证和发布

定向验证真实命令结果处理、部分成功、未知时间、错误目标、证据保护、批次续排、重复提交、超时和重启恢复；验证页面权限、CSRF、只读 GET 和新字段转义。执行相关 Python 测试、JS 语法与浏览器交互检查，不声称完成全量回归。部署前连接核对 201 并备份数据库、私有插件和旧镜像，仅部署已提交代码，不纳入本机未跟踪草稿。部署后对实测群启动一次正常同步，核对真实关系、时间缺失展示、服务健康并追加维护记录。
